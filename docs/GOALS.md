# 목적과 정보 구조

이 도구가 왜 있는지, 그리고 정리의 판단 기준이 되는 전제를 적는다. 화면 흐름은 [REDESIGN.md](REDESIGN.md), 분류 기준은 [../CLASSIFICATION_WORKFLOW.md](../CLASSIFICATION_WORKFLOW.md), 전체를 처음부터 다시 정리하는 절차는 [OVERHAUL.md](OVERHAUL.md)에 있다.

## 목적

ChatGPT를 장기간 쓰면서 **필요한 과거 맥락은 살리고, 오래되거나 무관한 맥락 때문에 답변 품질이 떨어지는 일을 줄이며, 사람이 대화 목록을 관리하는 부담도 줄인다.**

대화 정리 자체가 목적이 아니다. 판단이 갈리면 "앞으로 ChatGPT를 더 정확하고 적은 관리비용으로 쓸 수 있는가"로 정한다.

문제의 두 모습은 다음과 같다.

- 프로젝트에 넣지 않은 대화가 흩어져 있어 서로 맥락을 공유할 대화끼리 묶이지 않는다. 프로젝트로 구분하면 어느 정도 효과가 있으므로 프로젝트에 넣지 않은 대화를 알맞은 프로젝트로 옮기는 것이 핵심 용도다.
- 일상·가십·맥락 없는 일회성 질문이 최근 대화에 남아 있으면 다른 대화의 답변에서 예시로 끌려 들어오기도 한다. 업무와 무관한 일회성 대화는 골라내는 편이 좋다.

## 정보의 역할 분리

| 역할 | 무엇이 맡는가 | 규칙 |
| --- | --- | --- |
| **Source of Truth** | 실제 원본. GitHub repo가 있으면 그 repo(코드·문서), 회사·문서 업무는 해당 Google Drive 문서 등, 그 밖에는 가장 직접적이고 최신인 원자료 | 프로젝트의 현재 사실·상태는 원본에서 판단한다. 과거 대화와 원본이 충돌하면 대화로 현재 상태를 복원하지 않고 원본을 따른다 |
| **ChatGPT Project** | 지식베이스가 아니라 **서로 맥락을 공유할 가치가 있는 대화의 묶음(context boundary)** 이자 작업공간 | 핵심 질문: "이 대화들이 같은 프로젝트에 있으면서 서로를 과거 맥락으로 참조할 때 답변 품질에 도움이 되는가?" 관련이 약하거나 현재 상태가 서로 다른 대화를 억지로 합치지 않는다. 같은 repo·장기 작업·지속적 문제영역이면 한 프로젝트가 자연스럽다 |
| **Chat History** | 프로젝트의 현재 사실이 아니라 **작업 기록**: 조사 과정, 시행착오, 의사결정 과정, 당시의 가정, 과거 버전, 문제 해결, 아이디어 검토 | 모두 최신 지식으로 변환할 필요가 없다. 가치 있는 기록은 남기고, 향후 컨텍스트로 존재하는 것이 해롭거나 재사용 가치가 없으면 삭제후보로 보낸다 |

## 하지 않는 접근과 이유

대화를 주기적으로 요약해 `PROJECT_CONTEXT.md`·`STATE.md`·`DECISIONS.md` 같은 프로젝트 지식 문서로 쌓고(Google Drive 등) ChatGPT가 그것을 중심으로 이해하게 하는 방식은 쓰지 않는다. 이유:

1. AI용 지식 문서는 실제 원본보다 갱신이 늦어질 수 있다.
2. repo·업무 문서와 별도의 요약이 공존하면 서로 모순될 수 있다.
3. 프로젝트마다 지식베이스를 갱신하는 관리비용이 크다.
4. 오래된 대화 문제를 풀려다 또 하나의 오래될 수 있는 정보 계층이 생긴다.

ChatGPT 안에서(`@` 호출이나 프로젝트 지침으로) 정리를 시키는 방식도 쓰지 않는다. ChatGPT는 다른 대화의 전체 내역과 제목을 스스로 알지 못해(2026-09-26 시험) 대화 목록을 기준으로 한 정리가 성립하지 않는다. 정리는 이 도구 한 곳에서만 한다.

## 정리 기준 결정

| 항목 | 결정 |
| --- | --- |
| 삭제 강도 | **재사용 가치가 없으면 삭제후보로 보낸다.** 재사용 가치란, 향후 같은 프로젝트 대화가 참조할 결정·근거·조사결과·산출물·선호가 있고 그것이 원본(repo·문서)이나 후속 대화에 없는 경우를 말한다. 일상·가십·맥락 없는 일회성 질문도 삭제후보다(애매하면 사용자가 살린다) |
| 삭제 방식 | 기본은 지우지 않고 **삭제후보 프로젝트로 옮긴다.** 실제 삭제는 사용자가 ChatGPT에서 직접 한다. 영구 삭제는 고급 옵션이다 |
| 삭제후보 프로젝트 | 자동(기본 이름 `삭제후보`, 없으면 생성) · 정해 둔 프로젝트(없으면 기본 이름으로 생성) · 옮기지 않고 표시만(이미 프로젝트 안의 대화는 API로 뺄 수 없어 직접 빼야 함). 설정은 `.local/config.json`의 `trash`, 화면에서도 바꾼다 |
| 백업 | 별도 백업은 만들지 않는다. 다만 삭제 액션은 본문 사본(`runs/<id>/json/`)을 요구하므로 삭제 대상의 본문은 데이터 폴더에 남는다 |
| 제목 | 표준화는 필수다(목록 탐색용): `핵심 대상·주제 — 실제 작업 또는 결과`. 삭제후보로 옮기는 대화에도 적용한다(살릴 수도 있다) |
| 프로젝트 | 선택이다. 맞는 프로젝트가 없으면 프로젝트 없음이 정상이다. 새 프로젝트의 Memory 설정은 사용자가 직접 관리한다 |
| 분류체계 | 프로젝트 이름 체계(`YYMM` 목표형, `gh_` GitHub, 지속 영역 등)는 사용자의 `classification-taxonomy.md`를 참고만 한다. 전체를 본 뒤 더 나은 구조가 있으면 바꾼다 |
| 본문 노출 | 분석을 위해 대화 본문이 AI 모델에 노출되는 것을 허용한다. 제외할 프로젝트는 없다 |
| 검토 방식 | 전체 표를 다 보지 않는다. 요약을 보고 삭제후보·불확실 항목 중심으로 확인한다 |

## 조사 방식 결정

매번 전체 대화를 조사하지 않는다. 확인할 때 **범위를 고른다**.

| 범위 | 용도 |
| --- | --- |
| 프로젝트에 넣지 않은 대화 | 메인. 프로젝트로 정돈. 기간을 고른다(기본 14일 · 30일 · 전체). 프로젝트 목록은 읽지 않고 이전에 쓴 프로젝트를 옮길 후보로 쓴다 |
| 특정 프로젝트 | 작업을 마무리한 프로젝트를 정돈. 가장 빠르다(그 프로젝트만 읽는다) |
| 최근 N일 | 최근에 쌓인 것만 |
| 모든 대화 | 처음부터 다시 정리할 때(가끔) |

지난 확인과 비교하는 "기준 상태" 기록은 두지 않는다. 안전은 적용하면서 대화별로 다시 읽어 확인한 영수증과 실행 기록(`runs/<id>/`)이 맡는다.

## 목록 순서

ChatGPT 목록은 수정 시각 순이고 사용자는 대화의 위치로 대화를 기억하기도 한다. 실측(2026-09-26, 기존 실행 기록):

- **프로젝트 이동은 수정 시각을 바꾸지 않는다.** 삭제후보 프로젝트로 옮겨진 120건 전부가 이전과 같은 수정 시각을 유지했다.
- **제목 변경은 수정 시각을 변경 시각으로 갱신한다.** 제목을 바꾼 1건의 수정 시각이 06:53에서 변경 시각(07:46)으로 바뀌었다.

그래서 제목 변경 계획은 수정 시각 오름차순(오래된 대화부터)으로 만들고 한 번에 하나씩 적용해 **바꾼 대화끼리의 상대 순서**를 유지하며, 결과 화면이 그 순서를 확인해 알려 준다. 바꾼 대화가 바꾸지 않은 대화 위로 올라오는 것은 피할 수 없다.

## 피할 것

- 현재 프로젝트 구조를 옳다고 가정하고 기존 대화를 끼워 맞추는 것
- 앞부분의 대화만 보고 프로젝트 체계를 먼저 확정하는 것
- 모든 대화를 반드시 어떤 프로젝트에 넣으려는 것 (프로젝트 없음도 정상 상태다)
- 분야가 비슷하다는 이유로 지나치게 큰 프로젝트를 만들거나, 작은 차이로 지나치게 세분화하는 것
- 과거 대화 내용을 현재 사실로 자동 간주하는 것
- repo·업무 문서와 별도의 중복 지식베이스를 새로 만드는 것
- 오래됐다는 이유만으로 가치 있는 작업 기록을 지우는 것, 반대로 테스트·중복·잡음성 대화를 무조건 보존하는 것
