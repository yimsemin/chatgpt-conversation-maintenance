# 목적과 정보 구조

이 도구가 왜 있는지, 그리고 정리의 판단 기준이 되는 전제를 적는다. 절차는 [OVERHAUL.md](OVERHAUL.md)에 있다. 2026-09-25에 방향을 바꾼 결과이며, 이전 방향(대화 요약 → 프로젝트 지식 문서 축적)은 폐기했다.

## 목적

ChatGPT를 장기간 쓰면서 **필요한 과거 맥락은 살리고, 오래되거나 잘못된 맥락 때문에 답변 품질이 떨어지는 일을 줄이며, 사람이 대화 목록을 관리하는 부담도 줄인다.**

대화 정리 자체가 목적이 아니다. 판단이 갈리면 "앞으로 ChatGPT를 더 정확하고 적은 관리비용으로 쓸 수 있는가"로 정한다.

## 정보의 역할 분리

| 역할 | 무엇이 맡는가 | 규칙 |
| --- | --- | --- |
| **Source of Truth** | 실제 원본. GitHub repo가 있으면 그 repo(코드·문서), 회사·문서 업무는 해당 Google Drive 문서 등, 그 밖에는 가장 직접적이고 최신인 원자료 | 프로젝트의 현재 사실·상태는 원본에서 판단한다. 과거 대화와 원본이 충돌하면 대화로 현재 상태를 복원하지 않고 원본을 따른다 |
| **ChatGPT Project** | 지식베이스가 아니라 **서로 맥락을 공유할 가치가 있는 대화의 묶음(context boundary)** 이자 작업공간 | 핵심 질문: "이 대화들이 같은 프로젝트에 있으면서 서로를 과거 맥락으로 참조할 때 답변 품질에 도움이 되는가?" 관련이 약하거나 현재 상태가 서로 다른 대화를 억지로 합치지 않는다. 같은 repo·장기 작업·지속적 문제영역이면 한 프로젝트가 자연스럽다 |
| **Chat History** | 프로젝트의 현재 사실이 아니라 **작업 기록**: 조사 과정, 시행착오, 의사결정 과정, 당시의 가정, 과거 버전, 문제 해결, 아이디어 검토 | 모두 최신 지식으로 변환할 필요가 없다. 가치 있는 기록은 남기고, 향후 컨텍스트로 존재하는 것이 해롭거나 재사용 가치가 없으면 삭제한다 |

## 폐기한 방향

대화를 주기적으로 요약해 `PROJECT_CONTEXT.md`·`STATE.md`·`DECISIONS.md` 같은 프로젝트 지식 문서로 쌓고(Google Drive 등) ChatGPT가 그것을 중심으로 이해하게 하는 방식. 이유:

1. AI용 지식 문서는 실제 원본보다 갱신이 늦어질 수 있다.
2. repo·업무 문서와 별도의 요약이 공존하면 서로 모순될 수 있다.
3. 프로젝트마다 지식베이스를 갱신하는 관리비용이 크다.
4. 오래된 대화 문제를 풀려다 또 하나의 오래될 수 있는 정보 계층이 생긴다.

## 이번 전수 재정비에서 확정한 결정 (2026-09-25)

| 항목 | 결정 |
| --- | --- |
| 삭제 강도 | **재사용 가치가 없으면 삭제**한다. 재사용 가치란, 향후 같은 프로젝트 대화가 참조할 결정·근거·조사결과·산출물·선호가 있고 그것이 원본(repo·문서)이나 후속 대화에 없는 경우를 말한다 |
| 백업 | 별도 백업은 만들지 않는다. 다만 삭제 액션은 본문 사본(`runs/<id>/json/`)을 요구하므로 삭제 대상의 본문은 데이터 폴더에 남는다 |
| 분류체계 | 기존 안(`YYMM` 목표형, `gh_` GitHub, 지속 영역)은 **참고만** 한다. 로컬 폴더 체계와의 연결은 바람직하나 이번에는 보류. 전체를 본 뒤 더 나은 구조가 있으면 바꾼다 |
| 제목 | 현행 형식 유지: `핵심 대상·주제 — 실제 작업 또는 결과` |
| 범위 | **전체 대화를 처음부터** 다시 본다. 기존 프로젝트 배치가 잘못됐을 수 있다는 전제로 한다 |
| 본문 노출 | 분석을 위해 대화 본문이 AI 모델에 노출되는 것을 허용한다. 제외할 프로젝트는 없다 |
| 검토 방식 | 전체 표를 다 보지 않는다. 프로젝트 체계 승인 → 삭제 후보·불확실 항목 중심으로 확인한다 |

## 피할 것

- 현재 프로젝트 구조를 옳다고 가정하고 기존 대화를 끼워 맞추는 것
- 앞부분의 대화만 보고 프로젝트 체계를 먼저 확정하는 것
- 모든 대화를 반드시 어떤 프로젝트에 넣으려는 것 (프로젝트 없음도 정상 상태다)
- 분야가 비슷하다는 이유로 지나치게 큰 프로젝트를 만들거나, 작은 차이로 지나치게 세분화하는 것
- 과거 대화 내용을 현재 사실로 자동 간주하는 것
- repo·업무 문서와 별도의 중복 지식베이스를 새로 만드는 것
- 오래됐다는 이유만으로 가치 있는 작업 기록을 지우는 것, 반대로 테스트·중복·잡음성 대화를 무조건 보존하는 것

## 운영 방향 전환 (2026-09-26)

일회성 전수 재정비 뒤의 **평상시 운영 방식**을 바꾼다. 구현 현황: 범위 선택 조사, 삭제예정 프로젝트 기본화(설정 `trashProject`), 삭제예정 이동 대화의 표준 제목 필수는 구현됐다. 제목 변경 계획은 수정 시각 오름차순(오래된 대화부터)으로 만들고(`decision-compile.js`), 삭제예정 프로젝트가 설정돼 있으면 영구 삭제 선택은 검토 화면의 고급 접힘 안에 있다. 기준선은 가끔 확정하는 용도로 줄였다: 범위 조사의 적용 검증은 그 실행의 스캔 카탈로그 기준이고, 기준선은 건드린 대화의 항목만 고치며 확인 시각은 그대로 둔다(`checkpoint.js`, `baseline.js`의 `patchStateForTouched`). 남은 것: 기준선 없이 시작하기, 범위별 목록 조회 최적화. 현재 동작의 세부는 [REDESIGN.md](REDESIGN.md)와 코드가 정본이다.

| 항목 | 결정 |
| --- | --- |
| 범위 | 매번 전수 조사하지 않는다. **범위를 골라 조사**한다: ① 프로젝트 없는 대화(메인) ② 특정 프로젝트 ③ 최근 N일 ④ 전체(가끔, 보조) |
| ChatGPT 쪽 처리 | 하지 않는다. ChatGPT는 다른 대화의 전체 내역·제목을 알지 못해 `@` 호출이나 대화 안 정리가 성립하지 않았다. 정리는 이 도구에서만 한다 |
| 프로젝트 배치 | 프로젝트 없는 대화를 프로젝트로 옮기는 것이 핵심 목적이다. 일상·가십·맥락 없는 일회성 질문은 삭제 후보로 분류한다(애매하면 사용자가 살린다) |
| 삭제 | 기본 경로는 **삭제예정 프로젝트로 이동**이다. 그 프로젝트는 외부 메모리 참조를 끄고 사용자가 직접 만들어 도구에 지정한다. 영구 삭제는 사용자가 ChatGPT에서 직접 하며, 도구의 삭제 기능은 고급 기능으로 남긴다 |
| 제목 | 표준화는 필수다(목록 탐색용). 삭제예정으로 옮기는 대화에도 적용한다 |
| 목록 순서 | 아래 실측 결과에 따라, 제목 변경은 오래된 대화부터 처리하고 대상을 최소화한다 |

프로젝트 ID·주소는 저장소에 적지 않는다(`.local/config.json` 등 Git 밖에만 둔다).

### 수정 시각 실측 (2026-09-26)

기존 실행 기록으로 확인했다. 새 원격 변경은 하지 않았다.

- **프로젝트 이동은 수정 시각을 바꾸지 않는다.** 기준선 이후 삭제후보 프로젝트로 옮겨진 120건 전부가 이전과 같은 수정 시각을 유지했다.
- **제목 변경은 수정 시각을 변경 시각으로 갱신한다.** 2026-09-25 적용에서 제목을 바꾼 1건의 수정 시각이 06:53에서 변경 시각(07:46)으로 바뀌었다.
- 결론: 미배치 대화를 프로젝트로 옮기는 일은 순서를 해치지 않는다. 순서가 바뀌는 것은 제목 변경뿐이므로 제목 변경 대상을 최소화하고, 여러 건이면 오래된 것부터 처리해 처리한 대화끼리의 상대 순서만은 유지한다. 처리한 대화가 미처리 대화 위로 올라오는 것은 피할 수 없다.
