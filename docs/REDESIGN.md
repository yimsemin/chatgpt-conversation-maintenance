# 개편 설계 (정기 증분 정리 중심)

전수 재정비(2026-09)를 실제로 진행하며 드러난 사용 흐름의 문제를 고쳐, 이 도구를 **정기적으로 새 대화만 정리하는 도구**로 다듬는 계획이다. 목적은 [GOALS.md](GOALS.md)를 따른다. 확정한 결정(2026-09-25): 연결은 북마클릿을 유지하고 자동 복구를 강화한다 · 사용 패턴은 정기 증분 정리 · AI 분류는 지금 방식(대화창의 에이전트)을 유지하되 인계를 간소화한다.

## 전수 재정비([OVERHAUL.md](OVERHAUL.md))와의 관계

개편은 전수 재정비를 **끝낸 뒤** 시작하고, 재정비에서 얻은 것을 흡수한다.

- **P0 = 전수 재정비 마무리는 사용자가 ChatGPT에서 직접 한다**(`주식` 임시 보관 확인·삭제, 남길 대화 이동, 빈 옛 프로젝트 삭제). 개편 작업 중에는 ChatGPT에 접근하지 않는다(스캔·실측·변경 모두 없음). 개편이 끝나면 사용자가 정리한 계정을 **검증 단계**에서 처음 스캔해 기준선을 새로 만든다.
- OVERHAUL의 H(문서·원칙 갱신)는 P5의 문서 정리와 **한 번만** 한다. 중복해서 두 번 고치지 않는다.
- OVERHAUL이 만든 것 중 개편에 그대로 쓰는 것: 전수 수집(고급 옵션), 카드·조각·조립(`overhaul.js` → 일반 명령), 프로젝트 없음 허용, 빠른 검증, 25건 분할·자동 재개, 임시 보관(P4). 체계 초안·판정 파일 같은 일회성 산출물은 `data/`에 남기고 개편에서 다루지 않는다.
- 재정비 완료 후 `OVERHAUL.md`는 결과 요약만 남기고 절차는 이 문서로 넘긴다.

## 사용자 여정 기준 목표 (수용 기준)

단계는 시스템 층이 아니라 **사용자가 겪는 순간**으로 평가한다. 각 단계 끝에 아래를 실제로 재서 통과해야 완료다.

| 순간 | 목표 |
| --- | --- |
| 화면을 열었다 | 3초 안에 "연결됨/끊김(이유)", 새 대화 수, 검토 대기 수, 마지막 정리 결과를 본다. 어디까지 했는지 묻지 않아도 안다 |
| 정리를 시작한다 | 버튼 1번. 남은 시간(ETA)이 즉시 보이고, 새 대화가 적으면 1분 안에 끝난다(증분) |
| 기다린다 | 화면을 닫아도 작업이 계속되고, 다시 열면 진행 상태가 복원된다. 429·무응답으로 멈추면 이유와 자동 재개 시각이 보인다 |
| 검토한다 | 전체 표 없이 요약 한 화면 + 예외 목록. "무엇이 바뀌는가"를 적용 전에 안다 |
| 적용한다 | 버튼 1번. 내부 한도·해시·계획 파일이 보이지 않는다 |
| 끝났다 | 바뀐 것, 직접 할 일(비게 된 프로젝트 이름, 수동 제거 대화)이 결과 화면에 있다. 에이전트가 파일을 만들어 줄 필요가 없다 |

화면 시안(홈·검토·결과)을 만들어 사용자가 먼저 확인한 뒤 구현한다.

## 겪은 문제 (사실 기록)

| 영역 | 문제 |
| --- | --- |
| 연결 | 서버를 재시작할 때마다 릴레이를 다시 연결해야 한다. chatgpt.com 탭이 백그라운드이면 응답이 끊겨 90초 뒤 릴레이가 끊기고 작업 전체가 실패한다(2026-09-25). 연결됨 표시는 하트비트일 뿐 요청 성공이 아니다 |
| 시간 | 이동 1건에도 전체 카탈로그를 두 번(적용 전·후) 다시 수집한다(수 분). 전수 수집 451건은 1초 간격 + 429로 반나절. 429 뒤에는 사용자가 직접 재개해야 했다 |
| 가시성 | 진행 로그가 한 줄로 이어붙어 나오고 멈춘 것인지 진행 중인지 알 수 없다. 화면을 닫으면 작업 상태를 잃는다. ETA·현재 단계·남은 양이 없다 |
| 정보 부재 | 적용 전 "무엇이 바뀌는가"(삭제·이동·제목 수, 프로젝트별 증감), 삭제 후보 목록, 비게 되는 프로젝트 이름, 적용 후 결과 보고서가 화면에 없어 에이전트가 파일을 손으로 만들어 줘야 했다 |
| 흐름 | 스캔 → 요청문 복사 → 외부 AI → 붙여넣기 흐름이 길다. 실행 폴더·포인터·상태 해시 결속 때문에 이동 시험 1건에도 기준선·포인터를 백업/복구해야 했다. 25건·200건 같은 내부 한도가 사용자 오류로 노출됐다 |
| 구조 | 화면 906줄 단일 HTML, `maintenance-web.js` 900줄. 전수 재정비용 도구(`overhaul.js`)와 상시 흐름이 분리되어 있다 |

## 목표 흐름 (정기 증분)

1. **현황 홈**: 릴레이 상태(탭 전경 여부 포함), 프로젝트별 대화 수·최근 변경, 새 대화 수, 검토 대기 수, 마지막 정리와 결과. 가장 큰 버튼 하나: "새 대화 정리 시작".
2. **정리 세션**(상단 단계 표시, 어느 단계에서 닫아도 복귀 가능):
   1. 확인 — 증분 스캔(새·변경 대화만). 진행률·ETA·예상 요청 수를 보여 준다.
   2. 제안 — 에이전트에게 붙여넣을 한 줄과 필요한 파일 경로를 주고, 제안 파일이 생기면 화면이 자동으로 인식한다.
   3. 검토 — 요약(삭제·이동·제목·신규 프로젝트 건수, 프로젝트별 증감)을 먼저 보이고, 삭제 후보·확신 낮음·신규 프로젝트·이동만 예외로 펼친다. 검토 대기(임시 보관) 선택 가능.
   4. 적용 — 버튼 한 번. 백그라운드로 돌고, 일시적 실패는 자동 재개하며, 중단 가능. 진행률·ETA·최근 작업을 보인다.
   5. 결과 — 바뀐 내용 표, 프로젝트별 증감, **사용자가 직접 할 일**(비게 된 프로젝트 이름, 수동 제거 대화)을 그대로 보여 준다.
3. 전수 수집·재분류는 같은 세션의 옵션(고급)으로 둔다.

## 설계 원칙

- 사용자에게 내부 한도·해시·계획 파일 이름을 노출하지 않는다. 오류는 "무슨 일이 있었고 지금 무엇을 하면 되는지"로 쓴다.
- 작업 상태는 파일(`runs/<id>/`)이 정본이다. 화면·서버가 죽어도 이어 간다.
- 검증은 두 층: 대화별 재조회(항상) + 전체 재수집(요청 시·월 1회 등). 빠른 검증 기본.
- 원격 변경 승인 규칙(사용자 명시 승인·확인 문구·잠금·재조회 검증)은 그대로 유지한다.
- 코드는 AI를 호출하지 않는다. 에이전트 인계는 파일 계약으로 한다.

## 단계별 작업

### P1 신뢰성·가시성
- 릴레이: 서버 재시작 후 페이지가 스스로 재연결, chatgpt.com 탭 가시성·마지막 응답 시각 표시, 무응답 시 그 요청만 재시도, 요청 시간 초과 기준 분리.
- 작업 상태 영속: 작업 이벤트를 `runs/<id>/job.jsonl`에 남기고, 화면이 열릴 때 진행 중·최근 작업을 복원한다.
- 진행 표시: 단계·건수·경과·ETA. 로그는 줄 단위·타임스탬프·한국어.
- 오류 문구를 원인·조치 형식으로 통일하고 `PITFALLS.md`의 항목과 연결한다.

### P2 세션 모델·증분 스캔
- `pointer + phase` 문자열을 `runs/<id>/session.json` 상태 기계로 대체한다(brief·화면이 같은 정본을 읽는다).
- 기준선(`state.json`)과 실행의 해시 결속을 카탈로그 스냅샷 결속으로 바꿔, 부분 실행·시험 실행을 기준선 백업 없이 할 수 있게 한다.
- 증분 스캔: 최근 수정 순 목록을 알려진 구간에 닿을 때까지만 읽는다. 프로젝트 소속 정보의 출처는 실측(목록 응답에 포함되는지)한 뒤 결정한다.
- 요청 간격을 429 이력에 맞춰 조절하고, 쿨다운을 세션에 저장한다.

### P3 화면 재설계
- 단일 HTML을 모듈(현황·세션 단계·검토 표·결과)로 나눈다. 큰 표 대신 요약과 예외 목록을 기본으로 한다.
- 프로젝트 지도(프로젝트별 대화 수·최근 변경·비어 있음), 변경 미리보기, 결과 보고서.

### P4 검토 대기·후속 실행
- "삭제 후보 임시 보관"(이번에 `주식` 프로젝트로 한 방식)을 정식 기능으로: 보관 위치를 설정하고, 보관 목록 화면에서 남길 곳·삭제를 고르면 후속 실행을 자동 생성한다.
- 후속 실행은 이전 실행에서 파생(subset)한다.

### P5 정리
- `maintenance-web.js`를 세션·작업·라우트·검증 모듈로 분리, `overhaul.js`의 카드·조각·조립을 일반 명령으로 흡수.
- 문서: AGENTS.md·CLASSIFICATION_WORKFLOW·ARCHITECTURE·PITFALLS·OVERHAUL을 갱신하고 완료된 전수 재정비 절차는 요약만 남긴다.
- 테스트: 흐름 단위(스캔→제안→적용→결과) 테스트와 429·무응답 재현 테스트.

## 검증 단계 (개편 후, 사용자가 정리를 마친 계정으로)

모의 ChatGPT(429·무응답·지연 재현)로 구현하고 테스트한 뒤, 마지막에 실제 계정으로 전체 스캔 → 기준선 확정 → 정기 증분 시나리오(새 대화 몇 건 만들고 정리)를 돌려 수용 기준을 잰다. 아래 실측 질문도 이때 읽기 전용으로 확인하며, 구현은 두 경우(있음/없음)를 모두 지원해 실측 결과가 설계를 막지 않게 한다.
