# ChatGPT 대화 분류 지침

분류 요청의 결과물은 **현재 실행의 `proposal.json`**이다. 사용자는 화면에서 수집 범위를 정하고 제안을 검토·승인한 뒤 적용한다.

## 실행 순서

1. `npm run brief`로 현재 실행을 확인한다. 해당 실행의 `review.json`에서 후보와 `criteria`를 읽고, 데이터 폴더에 `classification-taxonomy.md`가 있으면 프로젝트 경계를 판단할 때 참고한다. [분류체계 예시](../templates/classification-taxonomy.example.md)
2. 후보마다 보존 여부, 제목, 최종 프로젝트를 정한다. 발췌만으로 판단하기 어려운 항목만 해당 원본 JSON을 읽는다. 원본과 다른 실행의 파일은 읽기 전용으로 다룬다.
3. 현재 실행 폴더의 `proposal.json`에 후보당 정확히 한 항목을 쓴다. 후보 식별 정보와 해시는 현재 인벤토리와 일치해야 한다. 적용 배치는 앱이 나누므로 25건 한도 때문에 제안을 나눌 필요는 없다.
4. 아래 명령으로 검증한다. 제목 길이·중복·프로젝트명 반복처럼 고칠 수 있는 경고는 직접 정리한 후 다시 검증한다. 사용자 판단이 필요한 항목과 검증 결과만 요약한다.

```text
node src/workflow.js validate-proposal <inventory.json> <proposal.json>
```

후보나 인벤토리가 바뀌면 새 실행을 기준으로 제안한다. 승인 파일의 작성, 실행 계획의 컴파일과 적용은 앱이 맡는다.

## 입력 기준

| 입력 | 사용하는 정보 |
| --- | --- |
| `review.json` | 현재 인벤토리 해시와 후보 본문의 해시에 연결된 발췌본. 사용자 메시지와 최종 응답, 첨부 이름·형식, 비텍스트 부분 개수, 프로젝트 문맥을 읽는다. 긴 메시지의 `head`·`tail`·`chars`와 `omittedMessages`는 생략 범위를 표시한다. |
| `inventory.json` | 후보 전체와 원래 제목·프로젝트·`reasons`의 기준. `projects`에서 기존에 쓸 수 있는 프로젝트를 확인한다. 범위에 따라 알려진 프로젝트 이름만 있을 수 있고, 읽지 않은 대화 수는 `null`이다. |
| 원본 JSON | 발췌에서 빠진 분기·첨부 참조·앞뒤 맥락 때문에 결론이 달라질 수 있는 대화만 확인한다. 첨부가 있다는 사실만으로 보존 또는 미결정을 고르지 않는다. |

`review.json`의 `criteria`는 이 문서의 요약이다. 세부 판단이 갈릴 때는 아래 기준을 사용한다.

## 분류 기준

현재 상태는 코드 저장소나 업무 문서 등 최신 원본으로 판단한다. ChatGPT 프로젝트는 같은 자료나 목적을 공유하는 대화의 작업공간이다. 대화 기록은 당시의 작업·결정·시행착오로 보고, 이후 답변에 쓸 가치와 유지 비용을 따져 분류한다.

| 제안 | 선택 조건 |
| --- | --- |
| `keep` | 고유한 결정·근거·선호·요구조건·조사·산출물·진행 맥락이 하나라도 있다. 보존할 부분과 불필요한 부분이 섞이면 대화 전체를 보존한다. |
| `delete` | 고유한 재사용 가치가 없고 삭제 근거가 있다. 테스트·잡음·중복·실패나 기각만 남은 대화, 무관한 일회성 질문, 다시 조사할 시점성 정보, 원본에 결과가 이미 반영된 대화가 해당한다. 현재 원본과 충돌하는 낡은 대화도 고유한 기록이 없다면 삭제후보다. |
| `undecided` | 판단에 필요한 근거가 발췌와 원본으로도 부족하다. 확인할 첨부, 원본 여부, 증빙 또는 의사결정 가치 등 남은 판단을 근거에 적는다. |

명시적 근거는 `high`, 내용상 추론은 `medium`으로 쓴다. `low`와 `undecided`는 함께 쓴다. 삭제 근거가 분명하고 고유한 내용이 없다면 `delete`로 제안한다. 오래됐다는 사실만으로는 삭제 근거가 되지 않는다.

**중복과 대체** — 조사·작성, 비교·결정, 설계·구현처럼 역할이 다르면 같은 주제라도 각각 보존한다. 후속 대화가 같은 작업의 갱신본이고, 그 대화만으로 최종 상태와 핵심 맥락을 설명할 수 있으며, 앞 대화에 고유한 자료·대안·근거·요구사항이 없을 때 대체로 판단한다.

## 제목 기준

- **`핵심 대상·주제 — 실제 작업 또는 결과`** 형식으로 쓴다. 구분자 ` — `는 정확히 한 번, 양쪽에 내용이 있어야 한다.
- 주된 목적과 실제 결과를 반영한다. 중복 제목은 고유한 초점으로 구분하고, 날짜·버전은 시점이 핵심일 때 넣는다. 막연한 상태 태그나 근거 없는 결론은 피한다.
- 최종 프로젝트명이 이미 알려 주는 주제 대신 이 대화를 구별하는 대상·작업을 제목에 쓴다. 프로젝트가 없으면 제목만 보고도 대상을 알 수 있게 쓴다.
- 공백을 포함해 15~35자를 기준으로 쓴다. 현재 제목이 표준 형식이고 구체적이며 경고가 없다면 `suggestedNewTitle: null`로 둔다.
- 삭제후보도 옮겨 둘 때 제목이 필요하다. 현재 제목이 표준 형식이면 `null`, 형식이 다르면 새 표준 제목을 제안한다.

## 프로젝트 기준

같은 고객·제품·자료·작업 목적이나 이어지는 산출물을 공유해, 앞으로 서로의 맥락을 참조할 때 도움이 되는 대화를 묶는다. 맞는 기존 프로젝트를 우선하고, 후속 대화에서도 재사용할 범위가 있을 때만 새 프로젝트를 제안한다. 어디에도 맞지 않으면 프로젝트 없음으로 둔다. 새 프로젝트의 Memory 설정은 사용자가 관리한다.

| 현재 상태 | 최종 목적지 | `suggestedProjectAction` |
| --- | --- | --- |
| 프로젝트 없음 | 프로젝트 없음 | `none` |
| 프로젝트 없음 | 기존 또는 새 프로젝트 | `use-or-create` |
| 프로젝트 안 | 같은 프로젝트 | `keep-current` |
| 프로젝트 안 | 다른 프로젝트 | `manual-move`. 사용자 승인 뒤 앱이 이동한다. |
| 프로젝트 안 | 프로젝트 없음 | `manual-remove`. 사용자가 ChatGPT에서 직접 뺀다. |
| 삭제후보 | 프로젝트 제안 생략 | `none`. `suggestedProjectName`과 `projectRationale`은 생략하거나 `null`로 둔다. |

## 제안 파일

`inventoryDigest`는 현재 `review.json`의 값을 복사하고, `scope.candidateCount`는 인벤토리의 후보 수로 맞춘다. `conversationId`, `currentTitle`, `projectName`, `reasons`는 원래 후보 값이다. `rationale`에는 대화별 판단 근거를 한 문장으로 쓴다. 목적지 프로젝트를 제안할 때는 이름과 배치 근거를 함께 쓴다.

```json
{
  "version": 1,
  "kind": "classification-proposals",
  "inventoryDigest": "현재 인벤토리의 SHA-256",
  "scope": { "candidateCount": 1 },
  "items": [
    {
      "conversationId": "대화 ID",
      "currentTitle": "오류 수정",
      "projectName": null,
      "reasons": ["scope"],
      "suggestedDecision": "keep",
      "suggestedNewTitle": "동기화 오류 — 재현 조건과 해결 검증",
      "suggestedProjectAction": "use-or-create",
      "suggestedProjectName": "데이터 파이프라인 운영",
      "confidence": "high",
      "rationale": "유사 장애를 진단할 때 필요한 재현 조건을 기록했다.",
      "projectRationale": "같은 동기화 작업의 장애 대응에 참고할 수 있다."
    }
  ]
}
```

### 승인 파일을 진단할 때

앱은 승인한 후보마다 `reviewed: true`와 `keep` 또는 `delete`를 기록한다. `delete`는 영구 삭제이고, 삭제후보 프로젝트 이동은 `keep`에 목적지와 `trashed: true`, 표시만 하는 경우는 `keep`에 `marked: true`다. `trashed`와 `marked`는 함께 쓰지 않는다. 제목 변경을 해제한 경우의 예외는 `keepTitle`이다. 파일 계약은 [구조 문서](ARCHITECTURE.md#파일-계약-누가-쓰고-누가-읽는가)에 있다.

## 파일 접근이 없는 AI에 분류 요청하기

아래 명령으로 현재 실행의 발췌본과 기준을 담은 요청문을 만든다. `prompt.md` 역시 현재 실행 폴더에 둔다. 사용자가 요청문을 전달하고 받은 JSON을 제안 화면에서 검증해 불러온다.

```text
node src/workflow.js claude-prompt <review.json> <prompt.md> [<inventory.json> <proposal.json>]
```

파일을 읽을 수 있는 에이전트에 저장·검증 경로까지 안내할 때는 인벤토리와 제안 경로를 마지막 두 인자로 함께 넘긴다.
