# 릴레이에서 반복해서 깨진 것들

릴레이·북마클릿·재시도·`src/server.js`를 고치기 전에만 읽는다. 진단에 가장 오래 걸린 항목이라 같은 함정을 다시 밟지 않도록 남긴다.

- **북마클릿 executor 안에 `//` 라인 주석을 두지 않는다.** `javascript:` URL은 저장·실행 과정에서 줄바꿈이 사라져 `//` 뒤 코드가 함수 끝까지 주석이 되고, 북마클릿이 통째로 죽는다(클릭해도 창이 열리지 않는다). 생성기 `inlineSource()`가 거부하고 테스트가 막지만, 설명은 executor 밖에 쓰거나 `/* */`를 쓴다.
- **로컬 검증 실패를 재시도 경로에 넣지 않는다.** `error.retryable = false`를 빼면 HTTP 상태 없는 `[retry]`가 지수 백오프로 반복되다 약 15분 뒤 실패한다. 화면에 원인이 전혀 드러나지 않는다.
- **식별자 정규식을 실측 없이 조이지 않는다.** 실제 ChatGPT 대화 ID는 RFC 4122 버전·variant 범위 밖이다(버전 니블 8 관측). 8-4-4-4-12 16진수까지만 강제한다. 경로 주입 차단에는 그것으로 충분하다.
- **릴레이 결과에는 대화 본문 전체가 실린다.** `/relay/result`만 64MB 한도를 쓴다(`bodyLimitForPath`). 다른 경로는 2MB. 한도가 모자라면 결과가 브로커에 닿지 못해 엉뚱하게 "relay timed out"으로 실패한다.
- **유지관리 창은 한 번에 하나만 연다.** 먼저 연결한 창이 릴레이를 소유하고 새 창은 거절된다. 빼앗게 두면 밀려난 창이 페이지 하트비트로 루프를 재시작해 양쪽이 서로를 무한히 밀어낸다.
- **화면의 `연결됨`은 원격 요청 성공을 뜻하지 않는다.** 하트비트만 확인한 상태다. 실패 위치는 `curl -s http://127.0.0.1:8523/relay/trace`로 본다(단계·op·요청 ID 앞 8자·HTTP 상태·경과 시간만 남는다).
- **변경 응답 200만으로 성공 처리하지 않는다.** `gizmo_id: null` PATCH는 200을 반환하고도 반영되지 않았다. 쓰기 뒤 재조회 검증을 유지한다.
- 429는 `src/relay-api.js`의 쿨다운·백오프로만 처리한다. 별도 대량 재시도를 추가하지 않는다.
- **HTTP 599는 ChatGPT의 응답이 아니다.** 페이지 실행기의 fetch 예외이거나 유지관리 창이 60초 안에 ChatGPT 탭의 응답을 받지 못한 경우(탭이 백그라운드이면 흔하다)다. 그 요청만 599 결과로 실패시켜 릴레이 루프를 유지하며, **읽기 op만** 자동 재시도한다. 쓰기 op는 결과가 모호하므로 반복하지 않는다.
- **전체 대화 목록만으로는 프로젝트 안의 대화를 다 얻지 못한다.** `/backend-api/conversations`는 프로젝트 대화의 약 20%를 주지 않는다(2026-09-25 실측). 그래서 프로젝트 범위는 그 프로젝트의 목록을 직접 읽고, 목록 기준인 범위(프로젝트 없는 대화, 최근 N일, 미정돈)는 프로젝트 안 대화가 빠질 수 있다. 프로젝트 없는 대화는 그 실측에서 빠진 적이 없다. 이 전제를 바꾸기 전에 `API_COMPATIBILITY.md`의 실측을 본다.
- **건너뛰기(`skipFailed`)의 4회는 릴레이 시도 횟수다.** `getConversation(id, { tries: 4 })`가 첫 시도를 포함해 4번만 시도하고 실패 결과를 돌려준다(끄면 릴레이 기본 재시도 8회 뒤 예외로 확인이 멈추고 자동 재개가 반복한다). 릴레이 연결 끊김 같은 예외는 건너뛰지 않고 확인이 멈춘다. 건너뛴 대화는 `inventory.warnings`가 아니라 `inventory.skipped`에 둔다(warnings가 있으면 컴파일이 거부된다).
- **이어받는 확인은 수정된 대화의 예전 본문을 다시 받는다.** 같은 범위 확인을 이어받을 때 대화 목록은 처음부터 다시 읽고, 받아 둔 본문은 목록의 수정 시각과 2초 안으로 같을 때만 재사용한다(엔드포인트마다 0.1~0.3초 어긋난다). 끊긴 사이 수정된 대화는 새로 받는다. 서버 종료로 남은 잠금은 같은 컴퓨터의 죽은 프로세스면 즉시 인수한다.
- **쓰기 요청 간격도 429 이력을 따른다.** 읽기와 쓰기가 같은 계정 한도를 쓰므로 `createPacer` 상태를 공유하고, 쓰기는 고정 간격(`requestDelayMs`)을 바닥으로 두되 429 뒤 늘어난 간격을 따른다. 재시도 안내는 `retryMessage`(`src/web-jobs.js`)가 만들며 429는 정상적인 자동 속도 조절로 표시한다. 적용 쪽 429 건너뛰기 설정은 만들지 않았다(쓰기는 순서·모호한 결과 때문에 건너뛰면 검증이 깨진다).
- **배치 계획 하나는 25건, 총 600건이다.** 큰 프로젝트는 같은 프로젝트를 가리키는 타깃 여러 개로 나뉜다(`compileProjectRouting`). 이 한도가 사용자 오류로 보이면 분할이 깨진 것이다.
- **삭제후보로 옮긴 대화는 표준 제목으로 바뀐 채 남는다.** 삭제 계획은 백업 JSON의 제목이 예상 제목과 같아야 하므로, 나중에 삭제를 확정하는 후속 실행은 제목만 현재 제목으로 바꾼 본문 사본을 그 실행 폴더에 새로 만들어 쓴다(`backupWithCurrentTitle`, 본문 해시는 mapping만 보므로 그대로다). 그 사이 사용자가 ChatGPT에서 제목을 바꿨다면 적용이 그 대화에서 안전하게 멈춘다.
- **제목 변경은 수정 시각을 바꾸고 프로젝트 이동은 바꾸지 않는다.** 그래서 제목 변경 계획은 오래된 대화부터 한 번에 하나씩 적용한다(`orderOldestFirst`, 순차 적용 한 경로뿐). 동시 적용을 도입하거나 정렬을 바꾸면 바꾼 대화끼리의 목록 순서가 뒤집힌다. 결과 화면의 순서 확인은 영수증에 남긴 수정 시각으로 한다.
- **자동 재개는 결과가 모호한 항목에서 멈춘다.** `Uncertain in-progress receipt actions`는 같은 쓰기를 반복하지 않으려는 의도적 중단이다. 원격 상태를 먼저 확인한다.
- **작업 폴더를 요청이나 실행 위치가 고르게 하지 않는다.** 앱 폴더(저장소 폴더)로 고정하고, 더블클릭·다른 폴더의 터미널에서 켜도 `src/launcher.js`가 그 폴더로 이동한다. 모의 서버는 `MAINTENANCE_ROOT`로 임시 폴더를 쓴다. 예전에 요청별 폴더 기본값 때문에 모의 서버 요청이 실제 데이터 폴더의 실행 기록에 쓰였고, 실행 위치에 따라 작업 폴더가 홈 폴더로 깨진 적도 있다.
- **앱을 백그라운드로 숨겨 켜지 않는다.** 예전 실행기는 서버를 분리(detached)해 로그 파일로만 출력했고, 사용자는 어떤 코드가 도는지·꺼졌는지 알 수 없어 낡은 프로세스가 남았다. 지금은 앱이 터미널 창의 프로세스로 돌고(창을 닫거나 Ctrl+C 로 종료), 하나만 켜지며, 화면이 프로세스 번호와 시작 뒤 코드 변경 여부를 보여 준다. 시험에서 자식 서버를 띄울 때는 시작에 실패해도 반드시 종료한다(남으면 다음 시험이 같은 포트에서 막힌다).
- 자동 시험이 서버를 띄울 때는 `MAINTENANCE_PORT`, 대기 시간을 줄일 때는 `MAINTENANCE_REQUEST_DELAY_MS`·`MAINTENANCE_RELAY_BACKOFF_MS`·`MAINTENANCE_RESUME_WAIT_SECONDS`를 쓴다. 실제 사용에서는 설정하지 않는다.
- **소유 창이 요청을 못 꺼내면 넘겨준다.** 백그라운드·최소화된 옛 창이 소유권을 쥐고 하트비트만 늦게 보내면 새 창은 "이미 소유됨"으로 거절되고, 첫 요청은 90초 뒤 "ChatGPT 페이지가 응답하지 않았습니다"로 실패한다(적용 첫 요청에서 막히는 증상). 요청 하나가 20초 넘게 꺼내지지 않으면 새로 연결을 요청한 창에 소유권을 넘긴다(`stuckMs`, 요청은 읽기라 자동 재시도). 원인은 대개 이전에 열린 앱 창·탭이 남아 있는 것이니 정리 창은 하나만 둔다.
- **정리 창은 하나다.** 북마클릿(chatgpt.com 탭)이 여는 `chatgptMaintenance` 창(`window.name`)이 정리 화면이면서 릴레이 연결도 맡는다. 창은 ChatGPT 탭이 열어 주어야(`window.opener`) 그 탭과 `postMessage`로 통신할 수 있으므로, 앱이 미리 열어 둔 일반 탭은 연결을 맡을 수 없다(그래서 앱은 브라우저 탭을 미리 열지 않는다). 다른 탭에서 화면을 봐도 작업은 시작할 수 있지만 정리 창을 닫으면 연결이 끊긴다. 정리 창을 최소화하면 타이머가 늦어져 클라이언트 교체(`Relay client was replaced`)가 날 수 있어 안내문에 닫거나 최소화하지 말라고 적었다. 예전에는 연결 전용 축약 창과 작업 탭을 나눴는데, 사용자가 창 두 개를 신경 써야 해서 합쳤다.
- **끊긴 확인은 같은 범위의 실행 폴더에서 이어받는다.** 범위별로 `scan-<범위 해시>-<run-id>`(전체 범위는 `overhaul-`) 폴더를 쓰고, 인벤토리가 없으며 24시간 안에 수정된 폴더를 `resumableRunDir`가 재사용한다. 예전에는 전체 범위만 이어받고 나머지는 시작마다 새 폴더라 취소 뒤 재시작하면 본문을 처음부터 다시 받았다(2026-09-28 실측: 186건을 받다 중단한 뒤 재시작이 0건부터). 범위 해시는 `validateScope`가 돌려준 값의 JSON이라 필드 순서를 바꾸면 이어받기가 끊긴다.
