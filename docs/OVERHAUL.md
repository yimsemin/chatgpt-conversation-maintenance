# 전체 재정비 운영 절차

전체 대화를 처음부터 다시 보고 프로젝트 체계·배치·제목·삭제를 한 번에 정하는 **드문** 작업의 절차다(평소에는 조사 범위를 골라 정리한다). 목적과 판단 전제는 [GOALS.md](GOALS.md)에 있다.

## 역할

- **사용자**: 화면 버튼(조사 범위 ‘모든 대화’로 확인, 결정 저장·적용), 프로젝트 체계 승인, 예외 검토, 빈 프로젝트 삭제 같은 수동 작업.
- **에이전트**: 도구 수정, 카드 생성, 체계 설계 초안, 판정, 제안 파일 작성, 검증. 스캔·적용은 대신 하지 않는다.

## 판정 기준

`CLASSIFICATION_WORKFLOW.md`를 기본으로 하되 이 작업에서는 아래가 우선한다.

- **삭제**: 재사용 가치가 없으면 삭제 후보로 보낸다(기본은 삭제후보 프로젝트로 이동). 다음은 삭제 후보다: 테스트·실수·잡음, 중복, 실패·중단만 남은 것, 완료된 일회성, 결과가 원본(repo·문서)에 이미 반영되어 대화에 고유한 것이 없는 것, 현재 원본과 충돌해 남으면 해로운 것.
- **보존**: 원본에 없는 결정·근거·기각한 대안·조사결과·산출물·사용자 선호가 있는 것. 오래됐다는 이유만으로 지우지 않는다.
- **불확실**: `undecided`로 두고 카드에 이유를 적는다. 남발하지 않는다.
- **repo가 있는 프로젝트**: 현재 repo(`gh`로 확인)가 진실이다. 대화 내용을 현재 상태로 간주하지 않는다.
- **프로젝트 배치**: "같은 프로젝트에 있으면서 서로 참조할 때 답변 품질에 도움이 되는가"로 정한다. 맞는 프로젝트가 없으면 프로젝트 없음이 정상이다.
- **제목**: `핵심 대상·주제 — 실제 작업 또는 결과`. 대화의 최종 내용을 반영한다(첫 질문이 아니라).
- 기존 프로젝트명·분류체계는 참고만 한다.

## 단계

1. **수집**: 조사 범위 ‘모든 대화’로 전체 대화 본문을 실행 폴더에 받는다(사용자 버튼, 끊기면 이어받는다). 삭제 액션이 본문 사본을 요구하므로 이것이 사실상 로컬 사본이 된다.
2. **카드화**: 인벤토리에서 만든 `review.json`을 크기 기준으로 조각내 병렬 에이전트에 나눠, 대화당 짧은 카드로 압축한다. 카드는 `runs/<id>/cards/`에 둔다. 조각을 나누는 기준은 프로젝트가 아니라 **무작위·균등**으로 한다(기존 분류에 끌려가지 않기 위해).
3. **체계 설계**: 모든 카드를 **한 컨텍스트에서 한꺼번에** 읽고 프로젝트 체계를 설계한다. 앞부분만 보고 확정하지 않는다. 결과는 프로젝트별 정의(범위·포함 기준·예상 대화 수·기존 프로젝트 대응)이며, **사용자 승인**을 받는다.
4. **판정**: 승인된 체계로 대화별 배치·제목·삭제를 정한다. 조각별 병렬 처리하되 체계와 기준은 동일하게 준다. 결과는 기존 `proposal.json` 스키마로 만들어 기존 검증기를 통과시킨다.
5. **검토**: 프로젝트별 요약, 삭제 후보 목록, `undecided`·확신 낮은 항목, 프로젝트 이동·신규 생성 목록만 확인한다. 전체 행을 보지 않는다.
6. **적용**: 화면 "적용". 배치 25건 단위, 429가 나면 쿨다운을 기다린다. 여러 세션에 나눠 진행할 수 있다.
7. **마무리**: 비어 있는 옛 프로젝트를 사용자가 정리하며, 이 작업으로 바뀐 원칙(`AGENTS.md`의 "분류와 적용", `CLASSIFICATION_WORKFLOW.md`, `docs/ARCHITECTURE.md`)을 문서에 반영한다.

### 카드 형식 (대화당 한 객체, 짧게)

```json
{
  "id": "대화 UUID",
  "topic": "주제 12자 이내",
  "refs": ["관련 repo·문서 이름"],
  "state": "active | done | superseded | oneoff | test",
  "value": "high | mid | low | none",
  "harm": "none | stale | conflicts-with-source",
  "why": "보존/삭제 근거 한 줄",
  "title": "표준 형식의 제목 초안 또는 null"
}
```

## 카드 도구 사용

```bash
node overhaul.js slice <inventory.json> <runs/id/slices> --parts N [--seed S]   # 무작위·균등 조각
node overhaul.js validate-cards <inventory.json> <runs/id/cards>               # 카드 형식·커버리지
node overhaul.js assemble <inventory.json> <runs/id/verdicts> <proposal.json>  # 판정 → proposal.json + 기존 검증
```

카드 파일은 조각마다 카드 배열(JSON), 판정 파일은 `{id, decision, title|null, project|null, confidence, why, projectWhy?}` 배열이다.

## 제약과 위험

- **프로젝트에서 대화를 뺄 수 없다.** `gizmo_id: null`은 200을 반환하고도 반영되지 않는다([API_COMPATIBILITY.md](../API_COMPATIBILITY.md)). 그래서 "프로젝트 없음"은 현재 프로젝트가 없는 대화에만 적용할 수 있다. 이미 프로젝트 안에 있는 대화를 프로젝트 없음으로 만들려면 사용자가 ChatGPT에서 직접 빼야 한다. 판정 결과에 `수동 제거` 목록으로 따로 보고하고, 그 전까지는 현재 프로젝트에 둔다.
- **프로젝트를 지우면 안의 대화가 함께 사라질 수 있다.** 빈 것을 확인하기 전에는 지우지 않는다. 옛 프로젝트 삭제는 모든 대화를 옮긴 뒤 사용자가 직접 한다.
- **영구 삭제는 되돌릴 수 없다.** 삭제 후보는 기본적으로 삭제후보 프로젝트로 옮기므로 영구 삭제는 고급 옵션이다. 별도 백업은 만들지 않으므로 영구 삭제를 켜면 적용 전 화면에서 목록으로 다시 확인하고 확인 문구를 요구한다.
- **429**: 2026-09-12 대량 적용에서 지속됐다. 쿨다운을 신뢰하고 반복 재시도를 추가하지 않는다. 배치 25건 제한을 유지한다.
- **변경 응답 200을 믿지 않는다.** 쓰기 뒤 재조회 검증을 유지한다.
- **모호한 쓰기**(프로젝트 생성)는 재시도하지 않고 원격 목록을 먼저 조회한다.
- 확인·적용은 로컬 잠금을 잡고 한다. 한 컴퓨터에서만 한다.
